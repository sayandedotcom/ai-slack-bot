# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Fire-Fighter Agent: one Cloudflare Worker that ingests every Slack message the team sees, wakes a generic Claude agent on the ones that matter, lets it fix bugs on a cloud container and open PRs under a fire-fighter's name, with every committal write gated behind one dashboard approval. Everything is one Worker, one origin (`firefighter.sayandeten.workers.dev`).

Two GitHub repos are in play — do not confuse them:
- **`Zellify/firefighter`** — this repo, the deliverable.
- **`Zellify/web2app-rebuild`** — Zellify's product monorepo. The agent clones it in the sandbox and opens PRs against its `staging` branch. Only the sandbox/ship code (`src/sandbox`, `src/git`) touches it.

## Commands

Monorepo: pnpm 10.33.4 + Turborepo, Node 22.20.0 (`.nvmrc`; `engines` is `>=22.20.0` and `.npmrc` sets `engine-strict=true`, so the wrong Node fails the install rather than a confusing runtime error later). Workspaces: `apps/worker` (the product), `apps/dashboard` (Vite/React SPA served by the Worker), `packages/ui|typescript-config`.

Root scripts: `pnpm build|dev|test|typecheck` fan out via turbo; `pnpm lint|format` are **Biome, run once at the root, not through turbo** — that is the only shape that reaches the 60 `.md` files, `spikes/` and `.github/` that no workspace owns. `pnpm check` is the whole gate in one command.

Almost all work happens in `apps/worker`:

```bash
pnpm install                          # once, at repo root — also installs the git hooks
pnpm check                            # THE GATE: check:text, lint, typecheck, capabilities:dts:check, test
pnpm format                           # biome check --write . — formats AND sorts imports
pnpm lint                             # biome ci . — writes nothing, errors only (warnings stay visible)

cd apps/worker
cp .dev.vars.example .dev.vars        # local secrets (gitignored) — needed for wrangler dev, NOT for tests
pnpm test                             # check-text-files.mjs + vitest run, in workerd against real D1/queues/DOs
pnpm typecheck                        # tsc --noEmit — REQUIRED alongside tests; vitest strips types
pnpm capabilities:dts:check               # generated capabilities.d.ts is in sync with the Zod schemas
npx vitest run test/agent-loop.test.ts            # one file
npx vitest run test/agent-loop.test.ts -t "steer"  # one test by name
pnpm test:watch
pnpm dev                              # wrangler dev on :8787 (needs ../dashboard/dist — build it first)
pnpm run deploy                       # builds the dashboard, then wrangler deploy (`run` — bare `pnpm deploy` is a pnpm builtin)
pnpm cf-typegen                       # regenerate worker-configuration.d.ts after any wrangler.jsonc binding change
pnpm run profile capture <name>       # snapshot every tenant-varying value (`run` — bare `pnpm profile` is an npm builtin)
pnpm run profile verify [<name>]      # check the loop-guard pins against the live bot token, and the AI Gateway
pnpm run profile apply <name>         # .dev.vars + wrangler.jsonc vars + `wrangler secret bulk`, in one step
pnpm capabilities:dts                 # regenerate src/capabilities/generated/capabilities.d.ts after any capability change
```

Dashboard (`apps/dashboard`): `pnpm dev` (vite, proxies `/api` — which carries the run SOCKET as well as JSON, hence `ws: true` — and `/ws` to :8787; `dev-stubs.ts` fakes the Access-gated identity/roster/approvals routes so the SPA renders locally). **The run socket, `POST /api/runs` and `GET /api/runs/:id` do NOT work on localhost**: they take an inner roster check and `wrangler dev` has no Access in front of it, so all three answer 401. That is documented in `dev-stubs.ts` and is deliberate — a stubbed socket would be a fiction of a live transcript. `pnpm build`, `pnpm test`, `pnpm typecheck`. `dist/` is gitignored and is the Worker's `ASSETS` directory, so a fresh checkout must build it before `wrangler dev`/`deploy`/the worker test pool will find it.

Next.js front-end (`apps/web`, added 2026-08-26): the second front-end, App Router, deployable to Vercel, sitting **beside** `apps/dashboard` — the Worker still serves the Vite SPA and `pnpm run deploy` is unchanged. Three routes: `/` (dashboard), `/chat` (a create form for `POST /api/runs`, nothing more), `/runs/[id]` (one run live over `/api/runs/:id/agent`, with that run's approval card inside the transcript). `NEXT_PUBLIC_DEMO=1 pnpm dev` renders every screen from `lib/fixtures` with no backend; `WORKER_ORIGIN=http://localhost:8787 pnpm dev` points the `next.config.ts` rewrite at `wrangler dev` — but **`POST /api/runs`, `GET /api/runs/:id` and the run socket all 401 against a local Worker**, because `requireTeamMember` wants a real Access JWT and `wrangler dev` has no Access in front of it (gaps §14; `apps/dashboard/dev-stubs.ts` refuses to stub the same three for the same reason). The run socket additionally needs `NEXT_PUBLIC_WORKER_ORIGIN` — **a Next rewrite proxies HTTP and does not carry a WebSocket upgrade**, so the Worker's host has to be in the bundle for the socket alone (`lib/api/socket-host.ts`). Reads go through TanStack Query (one cache, so panels each ask for what they need instead of the page fetching everything and prop-drilling it); `toPanelState` bridges a query into the same four-state `PanelState` contract the SPA uses. The one Zustand store is the approvals overlay (`lib/store/approvals-overlay.ts`) — a decided card lingering as a transient note, read by both the queue and the sidebar badge, and it never invents a decision. shadcn primitives all live in `packages/ui`; `apps/web/components.json` aliases `ui` there so `npx shadcn@latest add` keeps splitting them that way. **`apps/web/BACKEND-GAPS.md` is the list of everything the Worker does not provide** — chiefly that Access's cookie is scoped to the Worker's hostname, so a Vercel origin 401s on every request and demo mode is what deploys until that is answered; a WebSocket handshake is a subresource request, so the run socket fails there sooner than a fetch would. Its §7 and §8 exist to stop anyone re-adding the rotation and the "agent may act as me" toggle from the old prototype screenshots: neither has a source. §3–§5 are marked RESOLVED (the Agents-SDK chassis brought `POST /api/runs`, `GET /api/runs/:id` and the socket) and are kept rather than deleted. §13 is the one worth acting on: **nothing writes `runs.summary`** — `setRunSummary` in `src/run/repository.ts` has no callers and the INSERT writes `NULL`, so every run in both dashboards renders the empty-summary fallback. Only write a run over the socket through `steer`: `src/run/transport.ts` drops `cf_agent_use_chat_request`, `cf_agent_chat_clear`, `cf_agent_chat_request_cancel`, `cf_agent_tool_result` and `cf_agent_tool_approval` from every connection, so `sendMessage` fails silently. The two request-id rules are opposites — a create reuses its `clientRequestId` across retries, a steer mints a fresh one — and both are pinned in `apps/web/test/run-idempotency.test.ts`. Design spec: `docs/superpowers/specs/2026-08-26-nextjs-frontend-design.md` (D9–D13 cover the run route); plan: `docs/superpowers/plans/2026-08-26-nextjs-frontend.md` (see its 2026-08-27 addendum). `apps/web/AGENTS.md` and `apps/web/CLAUDE.md` are written by `next dev` itself — do not hand-edit them.

**The gate is `pnpm check` at the repository root** — control bytes, Biome, `tsc --noEmit`, generated declarations, then the suite, in that order (cheapest first). `.github/workflows/ci.yml` runs the same four jobs on every push and pull request. Run it yourself and establish the baseline before judging a change — do not trust a stated pass count. Commit after every task, conventional prefixes (`feat(scope):`, `fix(scope):`, `docs:`).

Git hooks are lefthook (`lefthook.yml`), installed by the root `prepare` script. **pre-commit**: Biome over staged files + the control-byte guard. **pre-push**: `typecheck` + `capabilities:dts:check`. The worker suite is deliberately NOT in a hook — 205–306s is a hook people learn to `--no-verify` past, which would cost the two fast checks as well. Escape hatches: `LEFTHOOK=0 git commit`, `git push --no-verify`.

Deploying is `workflow_dispatch` only (`.github/workflows/deploy-worker.yml`), behind a `production` environment and four preflight guards. **Never add a push trigger**: `wrangler.jsonc` runs a one-minute cron, so a deploy swaps the Worker under anything in flight.

Production secrets: `wrangler secret bulk` — never bare `wrangler secret put` from a non-interactive shell (uploads an empty string and reports success).

## Architecture (the big picture)

**One Worker, three entry points** (`apps/worker/src/index.ts`): Hono `fetch` (Slack webhook, `/api/*` — which carries the run socket at `/api/runs/:id/agent/*` as well as JSON — `/ws/*`, OAuth, `/proofs/*`, asset fallthrough), one `queue()` handler switching on `batch.queue` (`firefighter-ingest|memory|triage`), and a one-minute `scheduled()` cron running four independent repair sweeps (memory outbox, undelivered approvals, nudges, orphan sandboxes) via `Promise.allSettled`.

**One incident, end to end:**
1. `POST /slack/events` (`src/slack/events.ts`) — HMAC-verify (`src/slack/verify.ts`), then only a queue send. No D1, no fetch, within Slack's 3s.
2. Ingest consumer (`src/ingest/consumer.ts`, rules in `src/ingest/rules.ts`) — drops DMs/bots unconditionally, dedupes on `event_id`, writes `messages` (D1 is the system of record; every message verbatim with permalink), fans out to `MEMORY_QUEUE` always and `TRIAGE_QUEUE` only for triage-eligible channels. The app's own user-token posts classify as `ingested_self`: stored, remembered, never re-triaged (this is the loop guard).
3. Channel policy (`src/db/channels.ts`, `canPost()`/`getChannelPolicy()`): `observe` = ingest+triage, never post; `live` = postable (own test channels only); `internal` = no triage; unmapped = fail closed. `canPost()` is enforced inside the Slack binding, not in a prompt.
4. Triage (`src/triage/`) — Haiku emits `{ wake, why, opening_prompt }`; **never a ticket type**. A thread already owned by a run absorbs the message with no model call (`routeToOwnedRun`).
5. **RunAgent** (`src/run/agent.ts`, one Durable Object per run on `@cloudflare/think`; keys in `src/run/keys.ts` — the only `idFromName()` call site). Keyed `slack:{channel}:{thread_ts}` or `chat:{uuid}`; the public `runs.id` is a separate UUID resolved through D1, never string-built into a DO name. **There is one chassis.** `RunDO`, `src/run/chassis.ts` and the `RUN_CHASSIS` var were deleted on 2026-08-23 and rebuilt as this; nothing branches on a chassis anywhere.
   Think owns the session store, turn admission (`runTurn`), compaction, recovery and the `cf_agent_chat_*` protocol. This repo owns the policy, split by concern: `agent-prompt.ts` (context blocks + per-turn text), `agent-voice.ts` (the day-frozen engineer voice), `agent-channels.ts`, `agent-spend.ts` (the per-turn money ceiling), `agent-projection.ts` (status + usage into D1), `agent-steering.ts`, `agent-memory.ts` (the turn's episode), `transport.ts` (what a browser may say).
   `this.state` is the durable run state and it is BROADCAST to every connected browser — `runId`, `turnId`, `status`, `openApprovalId`, `lastApprovalId`, `channel`, `inputRevision`, and nothing sensitive, ever. `onStart` resolves `runs.key === this.name` through D1 so an object reached without a wake still knows its own public id.
6. **Wake paths** (`src/run/wake.ts`) — `wakeRun`, `routeToOwnedRun`, `createRunFromChat`, and there are no others. One shape: create-or-find the D1 row under the CURRENT channel policy (shadow ratchet, false→true only), `bindRun`, `noteInput()`, then `runTurn({ mode: "submit", idempotencyKey })`. **The D1 row is written before the object is addressed** — that ordering is what makes the write guard's call-time re-read authoritative and what makes the run addressable at all. `submit` returns before the turn runs (Think schedules a drain), so a wake is three fast RPCs.
7. Agent loop — Fable 5 through AI Gateway (`src/run/model.ts`; mandatory, no direct-Anthropic fallback), exactly one tool: `run_code`. Invariant 5 is enforced as `beforeTurn → activeTools: ["run_code"]`, NOT as a one-entry tool map: `createWorkspaceTools` is called unconditionally and always returns seven file tools, so `test/run-agent-boot.test.ts` pins the merged map as a tripwire instead. `src/run/model.ts` carries `installTestModel`, the seam a test uses to drive a real turn under the pool.
8. **Tier 1 execution** (`src/capabilities/`) — model-authored TypeScript runs in a Worker Loader isolate with `globalOutbound: null`, empty `env`, clamped CPU (`guarded-loader.ts`, `executor.ts` adds a parent-side timeout race). Its only reach is typed capabilities passed as RPC call *arguments*: slack, memory, linear, supabase, langsmith, betterstack, files, approval, sandbox, browser, github (`registry.ts`, `namespaces/*.ts`), wrapped as `CodemodeConnector`s by `connector.ts` with Zod rendered to JSON Schema (`schema.ts`). Every capability declares an `effect` (`read|external_write|control_write|sandbox_write`); `write-guard.ts` gates `external_write` on channel policy + shadow, re-read from D1 at call time; `effects.ts` is the D1 at-most-once ledger; `audit.ts` audits and budgets every call. **Every `read` is `replay: "reexecute"`** so its result never lands in codemode's durable `cm_log`, which stores args and results verbatim.
9. **Tier 2 execution** (`src/sandbox/`) — a `@cloudflare/sandbox` container per run (`run:{runId}`), pre-baked image with the monorepo, `provision.sh` boots asynchronously and its process table is the state. The container holds **no write credentials**: git's remote points at the sentinel host `git.firefighter.local`, and `Sandbox.outboundByHost` in `class.ts` swaps in `MONOREPO_PAT` at Worker egress. Dev-tier env is injected per process behind a boolean the model sets (`env.ts`), and known values are redacted from anything returning to the model. Teardown on terminal status + cron sweep.
9b. **Approval** (`src/approval/port.ts`, `notifier.ts`, `src/api/approvals.ts`) — `approval.escalate` writes the D1 card (`idx_approvals_one_open` is the guard, not the pre-check), sets `state.openApprovalId`, and schedules the nudge and a 6-hour expiry. `beforeToolCall` blocks every tool call while the flag is set. The human `PATCH`es (Access JWT + roster in `src/access/roster.ts`); a D1 CAS commits, then `makeRunAgentResolutionNotifier` settles delivery, **unparks the run, and only then submits** `approval:{id}` as a turn. Idempotency replaces the delivered-CAS: the cron re-submits unconditionally and every repeat is refused by the submission queue. `withdraw` loses honestly — a human who decided first gets their decision returned to the model instead of a withdrawal.
9c. **Transport** (`src/api/agents.ts`, `src/run/transport.ts`) — `/api/runs/:id/agent/*`, under `/api` so the socket and Think's `/get-messages` inherit the dashboard's Access application; `getAgentByName().fetch()`, never `routeAgentRequest`, so the private run key never appears in a URL. Every connection is readonly (that gates client state frames ONLY), and five chat frames — `chat-request`, `clear`, `cancel`, `tool-result`, `tool-approval` — are dropped by a filter installed **from `onStart`**, because Think installs its own protocol wrapper during `onStart` and a constructor-installed filter sits underneath it. Human input enters through one `@callable`: `steer`.
10. Notify (`src/notify/nudge.ts`) — one Block Kit DM per approval, claimed by CAS in D1. Bot token is for ingest/permalinks/nudges only; customer-facing speech always goes through a fire-fighter's own user token (`src/approval/sender.ts`, identities from `src/identity`, OAuth in `src/oauth`). **There is no on-duty rotation** (removed 2026-08-17): `src/identity/speaker.ts` picks the speaker — the approver if they clicked and have connected Slack, else the first `FIREFIGHTERS` entry (roster order) who has connected; nobody connected → every customer-facing write refuses, as before. The nudge DM and `GITHUB_AUTHOR=on-duty` use the same default speaker; the engineer-voice prompt block is frozen per UTC day, not per shift.
11. Ship (`src/git/`) — `sandbox.diff` → `apply.ts` (byte-exact unified diff, refuses renames/binaries) → `commit.ts` (blobs→tree→commit→ref→PR against pinned `GITHUB_REPO`/`GITHUB_BASE=staging`). Proof recordings go to R2 under `proofs/`, served Access-bypassed at `/proofs/:key`; other artifacts at `/api/artifacts` stay gated.

**Tracing:** the agent's own traces are the SDK's. Think emits GenAI OTLP spans through `wrapAISDK` and the Workers runtime exports them; there is no hand-written writer, no `dotted_order`, and no flush. The whole payload policy is two class fields on `RunAgent`: **`storeTools = true`** (a `run_code` span carries the model-authored program and what the capabilities answered — our code, our results) and **`storeMessages = false`**, which is all-or-nothing, so the customer's thread, the triage briefing and recalled memory never reach a third-party trace store. `beforeTurn` stamps `telemetry.metadata` and **overrides `agentId`**: Think's default is `this.name`, the PRIVATE run key, which would put `slack:{channel}:{thread_ts}` in the trace store for every customer conversation. The destination is a dashboard-side OTLP setting (LangSmith ingests at `/otel/v1/traces` with `x-api-key` + `Langsmith-Project`), not a var — `LANGSMITH_TRACING`, `LANGSMITH_TRACE_PROJECT` and `LANGSMITH_TRACE_PAYLOADS` were deleted with the writer that read them.

The LangSmith **READ** pin is a different thing entirely and must not be confused with it: `src/langsmith/client.ts` reads a CUSTOMER's traces as a capability (project `fire-fighter-standin`, by id, `POST /runs/query`). It shares only `LANGSMITH_API_KEY`. That key is scoped to ONE workspace and a project outside it is invisible rather than an error — a cross-workspace read returns `200` with zero runs — so the read pin and the trace destination must both live in `LANGSMITH_WORKSPACE_ID` (`be566aab-…`), which **also holds the live `zellify-prod` project; nothing is wired to it, deliberately**. Repointing the read pin there would let the agent surface real customer traffic into a Slack reply. Credential-shape scrubbing for outbound prose lives in `src/redact.ts`. `test/canary-secrets.test.ts` is what checks all of this: it drives one full run and sweeps every table in D1 and in the agent's own SQLite — enumerated from `sqlite_master`, never a list of names — for every secret-shaped binding.

**Memory:** Zep V3 graphs (`customer:{slug}` + `org`) are recall, not record; writes go through a D1 outbox → `MEMORY_QUEUE` → `src/memory/consumer.ts`, with the cron sweep as backstop. Citations resolve through D1 (`src/memory/cite.ts`).

## Conventions and traps

- **Deployment profiles** (`apps/worker/scripts/profile.mjs`, `config/profiles/*.json`, gitignored): pointing this Worker at a different org's Slack/GitHub/Linear/Supabase means moving ~39 values across three unrelated places — `.dev.vars`, the `vars` block of `wrangler.jsonc`, and Cloudflare's secret store — and nothing else checks the three agree. `apply` refuses a profile whose `SLACK_BOT_USER_ID` does not match `auth.test` on that profile's own bot token: that pin is the loop guard, and getting it wrong makes the agent re-ingest its own replies and answer itself, invisibly, until it is live. **`capture` before switching** or the setup being left behind is gone. It deliberately does NOT touch D1/R2/queue/DO bindings (swapping those swaps data), `src/access/roster.ts` (who may approve is code), or deploy for you.
- **Generated files — never hand-edit:** `apps/worker/worker-configuration.d.ts` (`pnpm cf-typegen`; only commit it from a real regeneration — it is machine-dependent on `.dev.vars` names, and running it **without** `.dev.vars` deletes every secret from `Cloudflare.Env` and breaks `tsc` in twenty places) and `apps/worker/src/capabilities/generated/capabilities.d.ts` (`pnpm capabilities:dts`). **Both are excluded from Biome in `biome.jsonc`, and that exclusion is load-bearing** — `capabilities:dts:check` compares the generated file BYTE-WISE against what `@cloudflare/codemode` renders (four-space indent, its own line breaks), so formatting it once makes the check fail permanently, and the only repair re-runs `--write`, which reverts the formatting, which the formatter re-applies.
- **`Env` type** lives in `src/index.ts`: `Cloudflare.Env` plus optional declarations for secrets and test opt-outs `wrangler types` cannot see. `wrangler.jsonc` `vars` are non-secret pins (vendor IDs, hosts, mode flags) deliberately kept in the repo; everything credential-shaped is a `wrangler secret`. Code names variables, never values, in errors/logs/health.
- **Adding a capability:** define it with `auditedCapability(...)` (a bare descriptor throws at registry construction), `effect` is required, append namespaces to the registry order (order = rendered `.d.ts` order), keep method names globally unique (generator emits un-namespaced `XInput`), regenerate the `.d.ts`, add `test/capabilities-<ns>.test.ts`. Zero-arg methods need `z.object({}).default({})`. Connectors pick it up automatically (`buildConnectors` maps the registry), but `test/capabilities-connector.test.ts` pins the surface count and sweeps every method for `requiresApproval` — never set it (spec D4: approval is a model-called capability, not a harness gate). Never hand a raw Zod schema to a connector: `toolInputSchema` accepts it silently and the model-facing type degrades to `unknown`.
- **The agent packages are exact-pinned** (`@cloudflare/think` 0.15.1, `agents` 0.20.1, `@cloudflare/codemode` 0.5.1, `@ai-sdk/react` 4.0.62) — no carets; `agents/codemode/ai` and `agents/ai-chat-agent` are removed entrypoints that throw at module evaluation. Read `dist/*.js`, not just the `.d.ts`, before writing against them. The traps that have cost real time, each one measured:
  - `createExecuteTool(this)` alone ships Think's default workspace as a `state.*` namespace — pass `state: undefined, browser: undefined` explicitly, even as undefined.
  - `CodemodeRuntime` must be in a `new_sqlite_classes` migration, not merely exported; `facets.get` is lazy, so only a call into it can tell.
  - **Never call `runTurn` from inside a DO RPC method — it deadlocks even unawaited.** Use `schedule(0, ...)`.
  - `runTurn` through a DO stub types as its LAST overload only; narrow with a local interface built from the package's own exported option types.
  - `beforeTurn`'s `instructions` REPLACES the assembled system prompt — append to `ctx.system` or every context block is silently dropped.
  - `createExecuteRuntime` has no `connectorHints`; a custom `description` DISCARDS Code Mode's own discovery text.
  - **Think installs its protocol `onMessage` wrapper during `onStart`, not the constructor** — a frame filter wrapped in the constructor sits underneath it and never sees a protocol frame. This one shipped broken until a test sent a real frame over a real socket.
  - `shouldConnectionBeReadonly` gates client STATE frames only. It gates no chat frame and no `@callable` — and `setState` throws inside a connection-scoped invocation, which is why `steer` mints its input revision from the alarm.
  - `TurnConfig.telemetry` is typed as `TelemetryOptions`, which has no `metadata`; Think reads `settings.metadata` at runtime anyway and spreads it into the runtime context. The shape it honours is not the shape it types.
  - A static import from a hook module of anything in the Worker entry's eager graph cannot be `vi.mock`ed under the pool.
  All recorded with file:line evidence in `phase-26-notes.md` (items 1–35) and summarised in the README's AI-tool notes.
- **Migrations are append-only** — `apps/worker/migrations/*.sql` (D1) and the `migrations` tags in `wrangler.jsonc` (DO SQLite classes). New DO class = new tag; never edit an existing one. Think owns `RunAgent`'s own schema, so there is no application-level DO schema version to bump any more.
- **`test/helpers/canned-model.ts` + `installTestModel`** are how a test drives a REAL turn. The pool binds `AGENT_MODEL_DISABLED=true` and empty Gateway settings, and a turn with no model behind it wedges the object — so before that seam existed, every wake path was unassertable past the submit. `toolCallingModel` drives a real `run_code` execution through the loader; `test/canary-secrets.test.ts` uses it.
- **Test files run SERIALLY** (`fileParallelism: false` in `vitest.config.ts`), and that is a correctness setting. Storage is shared across files, `test/approval-api.test.ts` wipes `runs` and `approvals` in its `beforeEach`, and suites that poll for an alarm's output stay live long enough to be inside that wipe. Observed once as seven failures across six files, green on the re-run.
- **Test harness** (`vitest.config.ts`, `test/setup.ts`): runs in workerd; migrations applied once; **storage is shared across tests and files (no `isolatedStorage`)** — mint a fresh run key per case (`chat:${crypto.randomUUID()}`), never assert absolute `seq`, never call `reset()`, never assume an empty DB. The pool binds synthetic vendor credentials (`not-a-real-*`), empty AI Gateway settings, `AGENT_MODEL_DISABLED=true`, `SANDBOX_DISABLED=true`, empty `NUDGE_FALLBACK_CHANNEL_ID`; suites that need a feature opt back in by passing their own env object. Those two `*_DISABLED` flags must never be set on a deployed Worker.
