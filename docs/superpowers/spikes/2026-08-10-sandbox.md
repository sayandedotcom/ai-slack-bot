# Spike findings — Cloudflare Sandbox (decision D5)

**Run:** 2026-08-11 · **Spike code:** `spikes/sandbox/` · **Consumed by:** Phases 18, 19, 20

**Environment:** `@cloudflare/sandbox` 0.12.5, `@cloudflare/containers` 0.3.7 (transitive), wrangler 4.120.0, deployed to `firefighter-spike-sandbox.sayandeten.workers.dev`.

**Container, confirmed on Cloudflare:** `standard-4` — 4 vCPU, 12220 MB, 18 GB disk, Linux 6.18 Firecracker microVM. Base image ships **Node 22.23.2 and git 2.34.1**, and **neither pnpm nor Chromium**.

---

## Verdict

> **GO on D5.** Cloudflare Sandbox does everything Phases 18–20 need. With a baked image the container reaches useful work in **~9 seconds**, the dev server serves publicly over a tunnel, a long-running server coexists with `exec`, a unified diff crosses container→Worker as a plain string, and the `interceptHttps` credential swap works exactly as `inspired-from-ronit.md` §7 describes — no version drift. **No fallback to E2B is needed and Phases 18–20 stand as written.**

The plan's fail bar for the warm install was eight minutes. It came in at **5.2 seconds**. The repro loop is not where this drill will be lost.

**The genuine unknown the roadmap named — "whether a `standard-4` container can run *Zellify's* monorepo" — is still open**, because the invite has not landed. What is now known is the platform's ceiling, measured against an equivalently-shaped repo. See [What this does not answer](#what-this-does-not-answer).

## 1. The six numbers

Measured on deployed Cloudflare containers, not locally. Stand-in repo: **`shadcn-ui/ui`** — pnpm + turborepo + a Next.js dev server, the same shape as this repo.

|---|---|---|---|
| 1 | Container cold boot | **3,592 ms** | **4,200 ms** |
| 2 | `git clone --depth 1` | **2,096 ms** | — (pre-cloned) |
| 3 | `pnpm install` (cold, no store) | **20,792 ms** | — |
| 4 | Dev server up and serving | **1,466 ms** | 1,466 ms |
| 5 | Chromium launch + navigate + `recordVideo` | **4,316 ms** | **6,034 ms** |
| 6 | `pnpm install --prefer-offline` (warm store) | **4,704 ms** | **5,231 ms** |

### Image rebuild

| | |
|---|---|
| Single-layer change on a cached base | **57 s** |

**Image size barely affects boot**: 3.06 GB cold-boots in 4.2s against 593 MB's 3.6s. Baking is close to free at boot and saves ~37s per run. Phase 18 should **not** treat the image as frozen, but should treat a Dockerfile edit as a several-minute round trip and iterate on the Worker instead.

## 2. The three Phase 19 capabilities — all pass

### Preview URLs — PASS

`sandbox.tunnels.get(5173)` returned `https://normally-listen-auto-geek.trycloudflare.com` in 7.4s, which served **HTTP 200 from the public internet**.

Two things that cost time:

- **`tunnels.*` requires `transport: "rpc"`** in `getSandbox` options. Without it: `Error: sandbox.tunnels.* requires the RPC transport.` It throws at **call** time, not construction, and the tunnels documentation never mentions it.
- **The tunnel needs ~10s to propagate.** Probing immediately after creation returns **530**. A retry loop is mandatory; a single probe reads as a broken tunnel.

`tunnels` is the right primitive over `exposePort()` regardless: the docs state preview URLs need a custom domain with wildcard DNS in production, while tunnels work on `.workers.dev`.

### Long-running process alongside `exec` — PASS

The dev server ran as a background process while `exec` calls executed against the same container: exit 0, output returned, 7 live processes. **This is the shape of the entire repro loop** — a server up while Playwright drives it — and it works.

### Diff extraction — PASS

439 ms, exit 0, a well-formed unified diff crossing container→Worker as a plain string:

```
diff --git a/SPIKE_MARKER.md b/SPIKE_MARKER.md
new file mode 100644
index 0000000..113634f
--- /dev/null
+++ b/SPIKE_MARKER.md
@@ -0,0 +1,3 @@
+# spike
```

**This is the whole credential story from D5** and it holds: the container emits an artifact, the Worker performs the write. Phase 20's design is unchanged.

## 3. Platform traps

Each of these cost real debugging time and none is in the documentation.

**Port 3000 is the sandbox's own control server.** `waitForPort(3000)` succeeds against *the sandbox itself* and reports a dev server that was never running — it returned a confident **752 ms** for a process that had already exited. `tunnels.get(3000)` at least fails loudly: `SandboxSecurityError: Invalid port number: 3000. Must be 1024-65535, excluding reserved ports.` **Phase 18 must bind the dev server somewhere else.** This is the worst trap here, because it fails by *succeeding*.

**`waitForPort` defaults to `mode: 'http'` and demands a success status.** An app that 500s on its own missing config is listening but reads as dead. `mode: 'tcp'` asks the question actually being asked — *is it listening* — and is what a repro loop wants.

**A process that fails `waitForPort` is not reaped.** It keeps running and holds its port, so the next attempt dies with `EADDRINUSE` and the real error is masked by a spurious one. Phase 18's lifecycle must own teardown; `killAllProcesses()` before start is the cheap fix.

**Deploying a new container image does not recycle a running container.** With `sleepAfter` set long, a live sandbox keeps serving the **old** image indefinitely — a rebuilt image silently has no effect, and `/env` cheerfully reports the old contents. `sandbox.destroy()` is what forces the next request onto the new image. It is also the primitive Phase 18 Task 4 needs for idle teardown.

**`wrangler deploy` returns before the new code serves.** New routes 404 for several seconds after a successful deploy. Twice this looked like a broken route.

**`NODE_PATH` must be set in the image.** A script in `/workspace` cannot `require()` a globally-installed `playwright` without `ENV NODE_PATH=/usr/local/lib/node_modules`.

## 4. `interceptHttps` + `outboundByHost` — PASS, no drift

Adapted from agent-os rather than discovered. It behaves exactly as `inspired-from-ronit.md` §7 records.

```json
{ "intercepted": true,
  "containerSentPlaceholder": true,
  "egressCarriedRealCredential": true }
containerFilesystemLeak: 0 occurrences
```

The container `curl`s `https://proxy.firefighter.local` carrying only `PLACEHOLDER_CREDENTIAL_NOT_A_SECRET`. The static `outboundByHost` handler runs **in the Worker**, swaps in the real secret, and forwards. The real value is confirmed on the wire by inspecting an echo service's reflection *in the Worker*; the container receives a boolean verdict, never the reflection — echoing the upstream response would hand the secret straight back inside and make the test assert the opposite of what it claims. `grep` across `/workspace`, `/tmp`, `/etc/environment` and the process environment finds **zero** occurrences.

**Sentinel-host mode confirmed:** with only `outboundByHost` set — no catch-all `outbound`, no `allowedHosts`/`deniedHosts` — every other host flows direct through the container's network namespace and never enters Worker fetch. This matters beyond tidiness: Worker fetch normalizes `Content-Length` on HEAD responses, which broke agent-os's s3fs-on-R2 mount.

**`sleepAfter` set to 45m**, deliberately, against the Task 2 timings. The SDK default of 10 minutes would have been marginal once the stand-in repo's 175s registry build is counted; a container that naps mid-repro is a drill failure.

### Where the API actually lives

`interceptHttps`, static `outboundByHost`, `allowedHosts`/`deniedHosts` and `sleepAfter` are **inherited from `Container` in `@cloudflare/containers` 0.3.7** — they are not declared on `@cloudflare/sandbox`'s `Sandbox`. Grepping the sandbox package for them finds nothing and reads as "these were removed."

**Newer than agent-os's notes**, and better for our use case: runtime per-instance overrides — `setOutboundByHost(host, methodName, params)`, `setOutboundByHosts`, `removeOutboundByHost` — resolving named methods from a `static outboundHandlers` map, plus an `outboundParams()` helper. Handlers receive `ctx = { containerId, className, params }`, so a handler can learn which run it is serving without the container naming it. **Phase 18 should prefer this to agent-os's module-scope static**, because our credential is per-run and per-engineer.

## What this does not answer

**Whether Zellify's monorepo runs in a `standard-4` container.** The roadmap named this as the genuine unknown and it remains one — the invite has not landed. This spike measured the platform's ceiling against an equivalently-shaped repo, which is what the plan asked for and is enough to call D5.

What would change the answer: a monorepo whose install or build exceeds the disk (18 GB) or memory (12 GiB) ceiling, or one needing services the container cannot host. The headroom observed is large — the baked image with a full `node_modules` used 3.4 GB of 18 GB, and memory never approached the limit — but that is the stand-in repo's appetite, not Zellify's.

## APIs the model expected that do not exist

For the README's AI-tool notes.

| Expected | Reality |
|---|---|
| `timeoutMs` on exec / port options | It is **`timeout`**. Produced confidently in three separate places. |
| `interceptHttps` / `outboundByHost` on `@cloudflare/sandbox` | Inherited from `Container` in `@cloudflare/containers`. |
| `corepack` available (Node 22 ships it) | Not on PATH in this image; pnpm must come from `npm i -g`. |
| Narrowing `sleepAfter` to `string` is safe | Breaks assignability to `SandboxEnv<Sandbox<any>>` — the namespace generic is invariant, so narrower fails exactly like wider, and the error surfaces at `proxyToSandbox()`, nowhere near the class. |
| `ContainerProxy` is internal | Must be **re-exported from the Worker entrypoint** or interception fails at runtime. Stated only in a comment inside the `.d.ts`. |
| `tunnels.get()` works on a default sandbox | Requires `transport: "rpc"`. |
| Docs pages carry the API surface | `/sandbox/`, `/sandbox/api/` and `/sandbox/configuration/` are hub pages; the surface is only on subpages. The `.d.ts` was the only reliable source throughout. |

## Actions for Phase 18

- Bake the image: pnpm, Playwright + Chromium, repo pre-cloned, warm store via `pnpm fetch`. Worth ~37s per run at almost no boot cost.
- **Do not bind the dev server to port 3000.**
- Use `mode: 'tcp'` for readiness, and `killAllProcesses()` before starting a server.
- Use `transport: "rpc"`, and retry tunnel probes for ~10s before calling one dead.
- Use `destroy()` for idle teardown — and remember it is also the only way to pick up a rebuilt image.
- Prefer runtime `setOutboundByHost` over the module-scope static, since the credential is per-run.
- Read the monorepo's root `AGENTS.md` first, as the brief says, and re-run §1's numbers against it once the invite lands.

## Reproducing

```bash
cd spikes/sandbox
cp dev.vars.example .dev.vars
pnpm install && npx wrangler types && npx wrangler deploy
S=https://<your-worker>.workers.dev

curl "$S/env"                       # container specs and what is installed
curl "$S/t2/boot"; curl "$S/t2/clone"
curl "$S/t2/install"                # and ?offline=1 for number 6
curl "$S/t2/devserver?port=5173&dir=apps/v4&script=dev"
curl "$S/t3/tunnel?port=5173"       # then retry the printed URL for ~10s
curl "$S/t3/diff"
curl "$S/t4/credential-swap"
curl "$S/destroy"                   # required after any Dockerfile change
```
